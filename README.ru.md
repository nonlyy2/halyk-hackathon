# covenant-agent

[English](README.md) · **Русский**

Читает «грязные» документы корпоративного кредитования — кредитные договоры, досье KYC,
аудиторские отчёты вперемешку с подсадными и недействующими редакциями под непрозрачными
хеш-именами — вместе с леджером транзакций без категорий, и для каждого финансового ковенанта
решает: **COMPLIANT** или **BREACH**, каково фактическое значение ограничиваемого показателя
(**actual**) и какая единственная транзакция служит **доказательством**, если она есть.

Результат — один `submission.json` по образцу `submission_template.json`.

## Установка

```bash
uv sync
cp .env.example .env                     # вписать один ключ
brew install tesseract tesseract-lang    # macOS; OCR-фолбэк для сканов
export COVENANT_DATA=/путь/к/датасету    # или --data в каждой команде
uv run covenant ping                     # отвечает ли выбранный провайдер?
```

Любой из `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GEMINI_API_KEY`, `HF_TOKEN`,
`ALIBABA_CLOUD_API_KEY` сам выбирает своего провайдера. Все провайдеры вызываются через голый
`httpx` — ставить SDK не нужно, и нет импорта, который мог бы упасть. Ключи перечитываются из
`.env` на каждом запросе, поэтому выгоревший можно заменить прямо во время прогона, не
перезапуская стадию.

`ping` делает один вызов на каждый уровень и печатает модель и задержку — либо ровно то, что
пошло не так. Запускайте его первым: изнутри работающей стадии плохой ключ неотличим от
сломанного пайплайна.

## Запуск

```bash
uv run covenant run --team КОМАНДА --contact-email you@example.com
```

Все стадии по порядку — classify, enrich, spec, bind, build, doctor. Упавшая стадия не
останавливает прогон: `build` деградирует, а не отказывается, поэтому дойти до него с частичными
артефактами лучше, чем не сдать ничего; упавшая стадия называется в конце, чтобы перезапустить её
отдельно.

```bash
uv run covenant classify              # документы -> тип + авторитетность
uv run covenant enrich --votes 3      # строки леджера -> категории, метки, правки аудитора
uv run covenant spec   --votes 3      # клаузулы -> формула, порог, период, оговорка
uv run covenant bind   --votes 3      # терм ковенанта -> транзакции, которые его образуют
uv run covenant doctor                # предполётная проверка: что может быть тихо неверно
uv run covenant build --team КОМАНДА --contact-email you@example.com
```

Каждая стадия кэшируется в `<data>/.cache/` и пропускает готовые сценарии, поэтому упавшая на
середине стоит только того, что не успела. `build` переписывает `submission.json` после каждого
сценария — валидный файл лежит на диске с первого же — и проверяет его в конце, завершаясь либо
`submittable: N cells, all template keys present and well-typed`, либо `UNSUBMITTABLE`. Это
единственная проверка в пайплайне без суждений: всё, о чём она сообщает, — факт, а не подозрение.

Кэши тегируются моделью, поэтому смена модели никогда не переиспользует чужие выводы.

`--votes 3` не опция: при одном голосе разбиение на категории плавает между прогонами, и ответ
плывёт вместе с ним; при трёх два подряд прогона дают побайтово одинаковые ячейки.

**Не передавайте `--review`.** Замерено на модели flash-класса: стоило 7.6 балла (33.0 → 25.4) —
на вопрос «что здесь не так» слабая модель находит что-нибудь. Ограничители при этом сработали:
каждая правка пересчитывалась, критик не мог назначить ни статус, ни значение, — то есть подвело
качество выбора, а не безопасность. Перед включением на сильной модели перемерьте, и только против
ключа.

## Как это устроено

**Языковые модели классифицируют, извлекают и выбирают. Считает Python.** Модели решают, *какие*
строки леджера учитываются и *как* они складываются; арифметику они не делают никогда. `actual`
оценивается по шкале, обнуляющейся при 5 % относительной погрешности, поэтому тихая арифметическая
описка стоит столько же, сколько отсутствие ответа. Каждая сумма, вычисление формулы и сравнение
происходят в детерминированном Python поверх ограниченного AST — никогда `eval` на непроверенном
выводе модели.

Числа берутся из леджера, кроме тех, что документы авторитетно задают или переопределяют:
переклассификация аудитора, раскрытая валютная пара, исправленная или отсутствующая сумма,
раскрытый, но не проведённый резерв, консолидированный показатель материнской компании.

```
src/covenant/
  config.py              все пути разрешаются один раз, из --data или COVENANT_DATA
  cli.py                 точка входа: classify / enrich / spec / bind / build / doctor / ping / score
  llm/client.py          выбор провайдера, цепочки запасных моделей, живое перечитывание ключа
  ingest/
    documents.py         текст через pypdfium2, постраничный OCR-фолбэк, кэш, сериализовано
                         (pdfium не потокобезопасен)
    ledger.py            префикс txn_id -> scenario_id; account_id <-> scenario_id из самих данных
    matching.py          документы -> сценарии, по номеру счёта, затем по имени заёмщика
    textnorm.py          нормализация гомоглифов и пробелов для разрежённого текста PDF
  analyze/
    classify.py          тип документа и говорит ли он за ковенанты
    clauses.py           нарезка текста клаузул, раздела владения KYC, приложения аудитора, с фолбэками
    documents_index.py   единственный поиск «какие документы говорят за этого заёмщика»
    enrich.py            категория транзакции, метки связанных сторон, правки аудитора
    spec.py              клаузула -> вычислимый спек (роли, формула, порог, оговорка)
    binding.py           терм ковенанта -> транзакции, которые его действительно образуют
    review.py            необязательное второе мнение по хрупким ячейкам (по умолчанию выключено)
  scoring/
    compute.py           детерминированный вычислитель
    confidence.py        сигналы хрупкости по ячейкам, для триажа
    rubric.py            dev-скорер, реализующий шкалу самого кейса
tools/perturb.py         строит возмущённый датасет для проверки переносимости
```

### Откуда берётся терм ковенанта

Клаузула называет статью учёта — «Операционные расходы по аудированной отчётности Заёмщика» — а
леджер сажает рядом с настоящей строкой куда более крупные аренду, ФОТ, маркетинг и страховку,
которые любой учебник тоже отнёс бы к операционным затратам. Раскладка по экономической сущности
читает терм на порядок шире, чем нужно, и метрику вместе с ним.

Поэтому состав решает `binding.py` — как задачу чтения по реальным транзакциям с текстом клаузулы
перед глазами, причём **порог клаузулы замаскирован**: выбирать строки и знать число, которое они
должны превысить, — две работы, которые не должны встречаться. Два терма не биндятся никогда:
агрегаты связанных сторон и неограниченных дочерних выводятся из таблицы KYC точным совпадением
имени, потому что датасет специально сажает лексически похожих подсадных контрагентов.

Ниже лежат детерминированные защиты, все независимые от модели. Выборка больше половины леджера —
не статья учёта; расходный терм в разы больше выручки — тоже; отношение, знаменатель которого равен
строкам числителя, — артефакт; метрика-коэффициент, в тысячу раз превышающая свой предел, посчитала
деньги, а не коэффициент; верхняя граница, проверенная против отрицательного значения, не соблюдена.
Клаузула с «разрешённой корзиной» содержит два числа, и лимит — только первое: корзина входит в
измеряемое, вычитается и ограничивается сверху, а модель, записавшая её ещё и как оговорку,
применяет её дважды. `doctor` сообщает всякий раз, когда защита отменила выбор модели, — именно эти
строки сильнее всего ограничивают, насколько правой позволено быть более сильной модели.

## Оценка при разработке

При наличии `ground_truth.json`:

```bash
uv run covenant build --team dev --contact-email dev@example.com --score
```

Применяет шкалу самого кейса: статус — 0.50 и гейт для всей ячейки, `actual` — затухание до нуля
при 5 %, доказательство — 0.20, которые при `null` в ключе едут вместе с `actual`. Печатает
невзвешенное среднее; настоящий лидерборд взвешивает ячейки по нераскрытому коэффициенту сложности,
поэтому это проверка логики, а не прогноз. **Боевой путь никогда не читает `ground_truth.json`.**

## Переносимость

В пайплайне нет захардкоженных идентификаторов сценариев, порогов, валют, названий компаний и
номеров ковенантов. Промпты сформулированы принципами, таксономия категорий выводится во время
работы, пороги и определения читаются из каждого документа.

Поскольку 36 ячеек с открытым ключом — плохой судья переносимости, `tools/perturb.py` строит
ближайшее подобие отложенной выборки: меняет то, что незнакомый набор вполне может сделать иначе,
сохраняя выводимость правильного ответа из старого ключа.

```bash
uv run python tools/perturb.py reformat --data data --out /tmp/pert  # номер статьи, заголовки пунктов и разделов
uv run python tools/perturb.py relabel  --data data --out /tmp/pert  # id сценариев, счетов, транзакций, порядок строк
uv run python tools/perturb.py rescale  --data data --out /tmp/pert  # все суммы и долларовые пороги ×1000
```

При `reformat` все 12 публичных сценариев по-прежнему нашли и нарезали каждую клаузулу, раздел
владения KYC разрешился, и 11 из 12 обогатились идентично — единственное расхождение в том, что
категория названа по-русски, а не по-английски. Счёт 32.2 против 33.5 на оригинале, и этот разрыв —
честное прочтение того, какая часть из 33.5 устойчива: две ячейки сдвигаются, потому что связанный
терм вобрал строки, которых не должен был, — при том что текст клаузул и все транзакции были теми
же. Границы термов — настоящая неопределённость, а не формат, арифметика или обвязка.

**Поднятие `--votes` этого не лечит, измерено.** При `--votes 5` 50 из 51 связанного терма
возвращаются идентичными `--votes 3`, и оба набора дают тот же счёт. Разброс выборки исчерпан —
модель отвечает на возмущённый вход уверенно и по-другому.

Оставшиеся датасет-специфичные литералы — повторяющиеся строки формата (названия заголовков, метки
недействительности), используемые как слайсеры, у каждой есть общий фолбэк, и `doctor` сообщает,
когда фолбэк сработал.

# Работа на незнакомом наборе

На оцениваемом наборе нет ключа. Ничто во время прогона не скажет, верен ли ответ, поэтому счёт там
не гонится. Чинить можно **механические отказы**: не найденный текст клаузулы, досье KYC, не давшее
владельцев, терм, который никто не связал, несконвертированную валюту, упавшую стадию. Каждый из них
стоит целых ячеек и каждый виден без ключа. Инструмент — `covenant doctor`.

Замерено на наборе из 27 сценариев и 84 ячеек: извлечение документов 10 с, `classify` ~5 мин,
`enrich --votes 3` ~12 мин, `spec` и `bind` по ~5 мин при `COVENANT_CONCURRENCY=4`. Время — не
ограничение; ограничение — диагностика упавшей стадии.

## Что сообщает `doctor`, по убыванию цены игнорирования

| Строка | Что значит | Действовать? |
|---|---|---|
| `no authoritative credit agreement` | У этих ячеек вообще нет текста ковенанта | **Да, в первую очередь.** Проверьте, не пометил ли `classify` все редакции недействующими |
| `no spec cache` / `no enriched cache` | Стадия упала для этого заёмщика | **Да.** Перезапустите стадию для одного сценария |
| `unresolvable formula variables` | Формула называет то, что ничем не заполнено | **Да.** `spec <sid> --fresh` |
| `clause headings not found` | Ковенант отвечен из фолбэка, а не из своей формулировки | **Да.** Откройте договор и посмотрите, как он озаглавливает пункты |
| `the spec calls its own formula approximate` | Модель сама написала «использовано как прокси» / «не может быть оценено» | **Да.** Это признание; читайте ведомость |
| `a guard discarded the model's own selection` | Детерминированная защита отменила выбор биндера | Читайте ведомость — верно при переширении, неверно при действительно широкой базе |
| `KYC ownership heading not found` | Фолбэк на весь текст досье — обычно работает | Только если ковенант о связанных сторонах нашёл ноль совпадений |
| `unbound terms [...]` | Биндер не ответил по терму, взята карта ролей | Низкий приоритет. Во многих сценариях корректно |
| `confidence=low/medium` | Тонкий запас или одна строка решает ячейку | **Без ключа не действие.** Информация, а не задача |

Последняя строка важнее всего тем, что запрещает. Тонкий запас — не доказательство ошибки, и
«починить» ячейку из-за узкого запаса значит изменить ответ без единого свидетельства, что он неверен.

## Как читать ведомость

```bash
python -c "import json;w=json.load(open('$COVENANT_DATA/.cache/worksheets.json'));print(json.dumps(w['<sid>']['<key>'],ensure_ascii=False,indent=2))"
```

По каждой ячейке: формула, каждый терм, какие строки его наполнили и подытог — единственный
артефакт, показывающий, *почему* получилось именно это число. Два отказа видны только здесь: терм из
одной строки там, где статья явно охватывает несколько (или наоборот), и приток, засчитанный как
выручка, но не являющийся продажей. Оба — суждения о документах, поэтому выносятся без ключа. Если
терм явно неверен, чините **принцип** в промпте `bind` и перезапускайте стадию — никогда не правьте
один сценарий руками и никогда не редактируйте `submission.json`.

## Если что-то пошло не так

| Симптом | Что делать |
|---|---|
| Стадия упала на одном сценарии | Ошибка ловится по сценарию, остальные доходят. Перезапустите стадию с id сценария |
| Квота кончилась посреди прогона | Клиент проваливается к следующей модели из `COVENANT_MODEL_*` и помнит мёртвую 10 минут. Добавьте имён и перезапустите — кэши дают продолжить |
| Ключ заменён на ходу | Подхватывается со следующего запроса; состояние выгоревших моделей сбрасывается вместе с ним |
| Ни один документ не признан авторитетным | Проверьте метку недействительности, совпавшую со всеми редакциями. `<data>/.cache/classifications.jsonl` даёт причину по каждому документу |
| Кончается время | Остановитесь на готовой стадии и запустите `build`. Он деградирует: нет биндинга → карта ролей, нет спека → порог ковенанта как `actual`. Никогда не сдавайте пустоту |

**Никогда** не запускайте `--fresh` на успешной стадии, если не готовы потратить её стоимость
заново. **Никогда** не правьте `submission.json` руками. **Никогда** не удаляйте каталог кэша.

# Что было сдано

Для приватного набора из 27 сценариев и 84 ячеек отправлено три ответа. Каждый заархивирован на
своей ветке с тегом вместе с кодом, который его произвёл.

| | ветка / тег | модель `complex` | модель `small` |
|---|---|---|---|
| v1 | `submission/v1-gptoss`, `submitted-v1` | `openai/gpt-oss-120b:cerebras` | `google/gemma-4-31B-it:cerebras` |
| v2 | `submission/v2-gptoss`, `submitted-v2` | `openai/gpt-oss-120b:cerebras` | `google/gemma-4-31B-it:cerebras` |
| v3 | `submission/v3-gemini`, `submitted-v3` | `gemini-3.1-flash-lite` | `gemini-3.1-flash-lite` |

Везде `--votes 3`. Обогащение общее, поэтому v3 отличается от v2 только моделью, построившей спеки
ковенантов и биндинги термов. Свежие `spec` + `bind` на той же модели воспроизводят те же ячейки в
точности — замерено на четырёх сценариях, 13 из 13 идентично.

## Бенчмарк моделей против публичного ключа

Каждая модель прогнала полные `spec` + `bind` на публичном наборе с одним и тем же общим
обогащением, поэтому единственная переменная — модель на уровне `complex`.

| модель `complex` | публичный 36 | возмущённый 36 |
|---|---|---|
| `gemini-3.1-flash-lite` | **33.5** | **32.2** |
| `qwen3.7-max` | **33.5** | не измерено |
| `qwen3-max` | **33.5** | не измерено |
| `openai/gpt-oss-120b:cerebras` | 32.5 | **32.2** |
| `qwen3.6-max-preview` | 32.5 | не измерено |
| `deepseek-v4-pro` | 32.2 | не измерено |
| `glm-5.2` | 31.5 | не измерено |

**Сила модели здесь не предсказывает балл.** Самая маленькая и дешёвая делит первое место, а две
заметно более крупные ей проигрывают. Промпты писались, глядя на отказы моделей flash-класса, и
более сильная модель читает те же инструкции иначе. Перед переходом на любую модель запустите
`covenant build --score` на публичном наборе — пять минут, и это отвечает на вопрос, на который
догадки не отвечают.

## Заведомо неверные ячейки

Проверено чтением текста клаузул, который кэшируется в `<data>/.cache/specs/*.json` под ключом
`"clauses"`. Ни одна версия не доминирует: каждая права там, где другая ошибается.

| ячейка | v2 | v3 | что говорит клаузула |
|---|---|---|---|
| `B5.6.1` | ✅ | ✗ | совокупный долг — «привлечённое за период финансирование»; v3 берёт балансовую цифру |
